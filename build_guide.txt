SortPi Landing Page Antigravity Build Guide

A detailed design and implementation prompt for a customer focused POS website

Prepared 27 October 2026 for GeekSSort. This guide replaces the earlier build prompt with a complete creative direction and sequential implementation prompts. It covers the landing page, demo conversion flow, contact experience, content rules and release checks.

How to use this guide

Save the supplied document and three images inside your Antigravity project under /reference. Name the images cta-reference.png, form-reference.png and contact-reference.png in their original order. Add real SortPi logos, product screenshots and approved customer assets under /public/assets. Open the existing website repository if available.

Paste Prompt 1 first. Then paste Prompts 2 through 10 in order, allowing each step to finish before continuing. Give Antigravity this entire guide as a reference file so later content requirements remain available. The prompts are implementation instructions, not marketing copy to display on the website. No separate Stitch output is required.

Research and design decisions

ChillyPOS

The homepage focuses on restaurant buyers, displays many named customers, explains product workflows, presents subscription plans and ends with an enquiry form. Its useful lesson is making the business context and customer proof visible. SortPi should use selective proof and understandable product demonstrations without adopting restaurant-only positioning, competitor performance claims or a long repeated customer wall. These are design recommendations, not measured conversion findings. Source: https://chillypos.com/ accessed 27 October 2026.

Mediasoft

The homepage combines broad industry navigation, demo and contact actions, customer logos, industry solutions and video testimonials. Its useful lesson is helping buyers identify their business type and reach a sales conversation. SortPi should offer a smaller set of relevant choices and simpler navigation rather than reproduce an extensive product directory. Competitor experience, customer counts and support claims must not transfer to SortPi. Source: https://mediasoftbd.com/ accessed 27 October 2026.

Image 2 contributes generous form spacing, readable input groups and a calm starting point. Adapt that pattern into a short demo request, not an account signup. Image 3 contributes a split contact introduction, supportive illustration and separate contact cards. Create an original SortPi composition with a product themed visual. Do not reuse Mediasoft artwork, office addresses, phone numbers or support hours.

What changes from the original prompt

The new prompt retains customer focus, every supplied core module, plan limits, existing routes, bilingual structure, accessibility, validation, SEO and performance checks. It resolves the inconsistent Book a demo, Start free trial, Try for free and Get started labels. Request Free Demo becomes the landing page conversion action; Contact Us is the secondary action.

Mandatory logo marquees, floating five star reviews, repeated statistics and video carousels become conditional on real assets. The first build uses clean product demonstrations when customer evidence is missing. Yearly pricing is hidden until approved. Stitch becomes optional inspiration. Implementation proceeds through clear stages rather than stopping for approval after every routine choice.

Prompt 1 Establish the brief and project foundation

Act as a senior product designer, conversion focused UX designer and frontend engineer. Build a distinctive SortPi marketing website for shop owners in Bangladesh. The site must explain daily business benefits, demonstrate the software clearly and generate qualified demo requests. It must feel like a carefully designed software product, with customer context and practical workflows throughout.

Read this full guide, the original SortPi document and all three reference images before implementation. Inspect the repository, existing design tokens, framework, routing, forms, CMS and assets. Identify what already works. Preserve existing business logic, authentication, blog URLs and application routes. Do not migrate frameworks for cosmetic reasons.

Use this precedence: current explicit requirements and supplied image direction; existing verified product configuration; the factual content in this guide; original document; competitor inspiration. If pricing conflicts, report the conflict in the implementation notes instead of silently selecting a new value. Never use competitor content as evidence of SortPi capabilities.

Create a brief implementation plan, route inventory, component map and content coverage checklist, then proceed with reversible local implementation. Only stop when an essential missing fact prevents a working integration. Keep independent design and frontend work moving. Do not publish, purchase services or send real test leads without explicit authorization.

For an empty project, use Next.js App Router, TypeScript and Tailwind CSS. For an existing project, follow its conventions and supported dependencies. Keep interactive islands small. Use CSS for routine transitions. Explain any added dependency in the build notes. Do not add a large animation library just for entrance effects.

Create typed content modules for site settings, navigation, features, industries, pricing, FAQs, testimonials, contact and translations. Separate sample dashboard fixtures from published product facts. Keep design tokens centralized. Suggested components: SiteHeader, Hero, CustomerProof, ProblemSolution, WorkflowExplorer, IndustrySelector, FeatureOverview, OwnerDashboard, SetupSteps, Pricing, CustomerStory, FAQ, BlogPreview, DemoSection, ContactSection and SiteFooter.

Preserve /signup, /signup?plan=starter, /signup?plan=standard, /signup?plan=business, /contact, /blog and existing /blog/[slug] routes. Inventory actual blog paths before editing. New demo CTAs lead to /#demo; Contact Us leads to /contact. Use root aware links from other routes.

Completion evidence: show the route map, design direction, missing asset inventory and proposed component hierarchy. Confirm how existing application behavior remains intact. Do not claim a build passes before running it.

Prompt 2 Create the visual system

Design concept: a clear view of the whole shop. Connect the shop floor with the owner's view through a recurring receipt, stock movement and dashboard motif. This is a visual story about one sale becoming useful business information. Avoid generic abstract technology graphics.

Use the existing approved SortPi brand color if available. Otherwise use this proposed palette from the CTA reference: primary #2563EB, hover #1D4ED8, ink #0F172A, body #475569, canvas #FFFFFF, soft surface #F6F8FC, border #E2E8F0. Reserve teal #0AC79E for subtle decorative accents and positive states with darker accessible text. Do not claim these are official brand tokens. Measure contrast for the final combinations.

Use Inter or the existing brand sans serif for English. Use Noto Sans Bengali for Bangla where available. Limit font weights to what the page needs. Set desktop H1 around 60px with 1.05 to 1.12 line height; mobile around 36px. Set section headings around 36 to 42px on desktop and 28 to 32px on mobile. Use 16 to 18px body text with approximately 1.6 line height. Never solve overflow by making essential text tiny.

Use a 1200px maximum content width, 24 to 32px desktop gutters and 20px mobile gutters. Base spacing on 8px increments. Give major sections 88 to 112px vertical padding on desktop and 56 to 72px on mobile. Use 16 to 24px card radii, restrained borders and soft shadows only where elevation explains hierarchy. Inputs and buttons should be at least 48px tall.

Build three distinct layout families: an editorial split for hero and contact, a product workspace for demonstrations, and concise comparison structures for pricing and features. Alternate white and pale surfaces. Use one navy owner dashboard section as a deliberate contrast moment. Avoid making every section the same three card grid.

Primary buttons: blue background, white label Request Free Demo, optional small diagonal arrow. Secondary buttons: navy background, white label Contact Us, optional right arrow. Keep arrows decorative to assistive technology. On dark sections, use an accessible contrasting secondary treatment. Never place two equally prominent primary actions beside each other.

Use icons from one consistent set, around 20 to 24px, with matching stroke weights. Decorative dots may appear faintly behind contact content, inspired by image 3. Do not put patterns beneath dense copy or form controls. Do not add floating decorative objects without a clear role.

Motion: 160 to 220ms for buttons and tabs, gentle 240ms reveals when appropriate. Content must remain visible if JavaScript fails. Respect reduced motion. No scroll hijacking, forced horizontal page scrolling, autoplay video, spinning gradients, custom cursor or excessive parallax.

Create a small component preview with buttons, headings, input states, cards, tabs and alert messages before composing the page. Check keyboard focus and contrast now. Deliver the token definitions and a screenshot of this preview as implementation evidence.

Prompt 4 Build the product story and industry selection

Create a compact problem and answer section headed Less chasing records. More control over the day. Pair four problems with outcomes: separate sales and stock records become connected transactions; uncertain dues become customer balances; unclear spending becomes income and expense visibility; branch phone calls become branch level reporting. Use short horizontal rows or an asymmetric layout instead of four generic stock icons.

Build the signature WorkflowExplorer headed See what happens after every sale. Four numbered controls select Sell, Update stock, Track dues and Review reports. The main screen changes to match the selected task. Keep the panel height stable. Use accessible tab roles, arrow key navigation and visible active states. Do not auto advance.

Sell shows the BDT 900 sample cart. Update stock shows the exact three inventory movements. Track dues uses the same sale in a clearly labelled alternative payment example: paid BDT 700, due BDT 200. Review reports reflects only the selected example, with consistent totals. Reset restores the full payment scenario. Explain that these are interactive sample screens, not access to a real merchant account.

Use a thin visual connector between the selected control and relevant screen region on desktop. On mobile, show the controls above the panel with short labels. The complete content must remain accessible without hover. Do not implement a pretend scanner, real checkout or payment gateway in this marketing demonstration.

Create an industry selector headed Built around the way your business sells. Use six choices: Retail shops; Super shops and grocery; Restaurants; Pharmacies; Wholesale; Multi branch businesses. Selection changes a short use case, three applicable capabilities and a relevant sample screen. Keep all choices visible without relying on color alone.

Retail: sales, customer purchase history, dues. Super shops and grocery: product stock, purchases, low stock visibility. Restaurants: general billing, expenses and reports only. Pharmacies: general product stock and sales only. Wholesale: supplier purchases, customer dues and sales records. Multi branch: separate stock and sales, branch reports and configured transfers.

Do not imply KOT, table management, medicine expiry, batch tracking, regulated compliance, weighing scale support or offline operation. Those remain unconfirmed. Industry headings are use case navigation, not claims of specialized capabilities.

Use one module link beneath this section to focus #features. A chosen industry can preselect Business type in the demo form, but it must remain editable. Announce content updates accessibly without repeatedly moving keyboard focus.

Prompt 5 Build the feature overview owner view and setup journey

Use compact rows or smaller panels for the rest. Each item needs a concrete outcome and, where useful, a miniature UI detail rather than decorative artwork.

Inventory: product management, stock updates after sales and purchases, low stock warnings and branch stock transfers where configured.

Purchases and suppliers: purchase records and supplier dues.

Customers and dues: purchase history, purchase frequency, spending and outstanding balances.

Expenses and accounts: income, expenses, cash flow, net profit, cash in hand and payment history. Describe visibility, not an audit guarantee.

Reports: sales, profit, stock, purchases, expenses and staff reports by day, month or branch; print or download.

HR and payroll: retain this module without adding unsupported attendance devices or payroll rules.

Multi branch control: separate stock, sales and staff for each branch, with individual and combined views.

Users and access: team accounts and role based access.

Dashboard and device access: sales due, net profit, expenses, purchase due, low stock products, stock alerts and daily target; access across supported device layouts.

Create a dark navy owner view headed Know what needs your attention. Show a clean sample dashboard with an understated branch selector. Highlight Sales, Customer dues and Low stock. Prompt 8 Implement reliable interactions and bilingual content

Implement POST /api/demo-request or use the established backend contract. Validate all fields on both client and server. Normalize Bangladeshi phone input by removing formatting and converting local numbers to +880 format. Accept local ^01[3-9][0-9]{8}$ or international ^\+8801[3-9][0-9]{8}$. If supporting Bengali digits, normalize them before validation. Test valid, invalid and empty values.

Forward validated requests to a server configured DEMO_WEBHOOK_URL. Never accept a destination URL from user input. Keep secrets server side. Set timeouts, inspect upstream status and prevent duplicate submissions through idempotency keys. Use a hidden honeypot and a production suitable shared rate limiter; an in memory limiter is development only on distributed hosting.

When the webhook is missing in development, return an explicit preview mode response without claiming delivery. In production, return a safe error and provide phone and email alternatives. Avoid logging names, phone numbers and messages by default. Do not expose upstream errors or credentials. Provide .env.example with variable names and setup guidance only.

Success text: Your request has been received. The SortPi team will contact you using the details you provided. Failure text: We could not send your request. Please try again or contact us directly. Announce errors and success using an appropriate live region. Move focus to an error summary when needed. Retain entered values on failure.

Internationalization applies to the marketing site only. Do not imply the POS application or printed receipts support Bangla. Use an existing locale system if present; otherwise create a complete en and bn dictionary. Translate navigation, body copy, form labels, validation, selected states, FAQs, metadata and accessibility labels. Mark translations requiring review in private content metadata, not in visitor facing text.

Persist locale choice in a cookie compatible with server rendering and update html lang. Prevent hydration mismatch and English flashes after selecting Bangla. Allow longer copy and proper Bengali line height. Use human review before public launch. Do not introduce /bn routes casually if the existing routing strategy uses a language preference instead.

Create a small analytics adapter with typed events: demo_cta_click, contact_cta_click, pricing_plan_selected, industry_selected, workflow_step_selected, demo_form_submit, demo_form_success, demo_form_error, language_change and video_play when applicable. Preserve old analytics event mappings only if existing reporting needs them. Include section and plan as safe properties; never include names, numbers, email or message contents.

No external analytics calls unless a real provider is configured and the site's consent requirements are handled. A public analytics ID is an identifier, not authorization to invent a provider integration. Keep the unconfigured adapter as a documented no-op.
